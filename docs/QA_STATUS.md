## What is proven

**Unit/integration (vitest):**
- 209 test files, 8778 tests passing (12 skipped), ~5s runtime, verified 2026-07-04 on branch `hardening/my-kora-server-guard` (MYKORA-01) via `npm test`.
- Includes static/structural version-consistency tests (e.g. `b100-versioning-consistency.test.ts`) that assert forbidden stale labels don't appear in client-facing strings, tenant-isolation source-analysis tests, and role/auth-routing structural tests.
- **Important caveat on what these prove:** most of this suite is static source-code analysis (reading files as text, asserting patterns) or pure-function logic testing — not runtime rendering or live-database verification. A test named "golden path" or "tenant isolation" in this suite does not necessarily mean the actual runtime behavior was exercised end-to-end; check what a given test file actually does before citing it as proof of a live behavior.

**MYKORA-01 — `/my-kora` server-side guard (2026-07-04):** `app/my-kora/layout.tsx` converted from client-side session detection to a server-side guard (`getSessionKoraRole()`, additive to `lib/auth/kora-session.ts`), closing PILOT_SAAS_READINESS.md blocker #5. New coverage: `tests/unit/mykora-01-server-guard.test.ts` (structural — asserts the layout has no `'use client'` directive, resolves the session server-side, hard-blocks any non-WORKER/non-KORA_ADMIN real session before rendering children, and only reaches the client-side `MyKoraDemoGate.tsx` when there is no real session at all). Existing structural suites touching this layout (`b141b-my-kora-pib-ia-and-admin-access.test.ts`, `b151a-demo-live-sidebar-worker-gate.test.ts`, `b81b-worker-identity-foundation.test.ts`) were updated to match the new file split rather than the old single-file client gate. **Not covered:** no authenticated E2E exercises `/my-kora` under a real WORKER/COMPANY_ADMIN/PARTNER session (static/unit only, per sprint scope — authenticated staging E2E explicitly deferred).

**RLS negative testing, local direct-Postgres (RLS-03, merged to `main` via PR #26):**
- `tests/integration/rls-two-tenant-negative.test.ts` connects directly to a local Supabase Postgres instance (`pg`, no PostgREST/`@supabase/supabase-js` involved) and proves Postgres RLS itself — not application code — rejects cross-tenant reads on `analytics.source_batch`, `analytics.kora_index_result`, and `analytics.activation_result`. Own-tenant reads (positive control) pass and cross-tenant reads return zero rows, for both synthetic tenants in both directions.
- Run 2026-07-04 against local Supabase (migrations `001`–`028`, `030`, `031` applied, no seed): **13/13 tests passed** (`RLS03_ALLOW_RUN=true RLS03_PG_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres npm test -- tests/integration/rls-two-tenant-negative.test.ts`). Synthetic fixture rows fully cleaned up afterward (verified directly against the DB). No cloud/staging/production Supabase or Vercel involved at any point.
- **What this does NOT prove:** GoTrue/Supabase Auth sign-in (claims are simulated via a transaction-local `request.jwt.claims` GUC, not a real signed-in session), PostgREST schema-exposure correctness (this test never goes through PostgREST — `analytics`/`personal`/`commons`/`gov`/`audit`/`network` remain unexposed via the API), browser/authenticated E2E flows (RLS-04/05), worker-vs-worker isolation (`personal.*`, reserved for RLS-05), or report/export-level privacy suppression. Skip-safe by default (`RLS03_ALLOW_RUN` unset in CI/normal `npm test` runs).

**App/API tenant enforcement audit (RLS-04, 2026-07-04):** Static audit of every `app/api/**` route (84 route files) mapping which auth guard each uses (`requireCompanyUser`/`requireWorkerUser`/`requirePartnerUser`/`requireKoraAdmin`/`requireDemoUser`), which routes use the service-role client (all 36 confined to `app/api/admin/**`, all `requireKoraAdmin`-gated), and whether any route accepts `tenant_id`/`worker_id` from a client-controlled body/query/param instead of session `app_metadata`. Finding: no route did — this was already true going in, hardened by prior sprints (RLS-03, B168, ROLE-01). New coverage added, `tests/unit/rls04-app-api-tenant-enforcement.test.ts`, filling three gaps the existing `tenant-isolation.test.ts`/`route-privacy.test.ts` suites (scoped to `app/api/company/**` and `app/api/admin/**`) didn't reach:
  1. Worker routes (`app/api/worker/**`) never accept `requireCompanyUser`/`requirePartnerUser` as an alternate auth path.
  2. PARTNER API isolation is pinned: `app/api/partner/**` does not exist yet, and no route under company/worker/admin/commons imports `requirePartnerUser` — if either changes, this test forces a deliberate update rather than a silent gap (PARTNER auth today is enforced entirely at the page/layout level, not via API routes — see `app/partner/layout.tsx`, `requirePartnerUser()`, already covered by `b127-partner-workspace.test.ts`/`partner-01-pilot-surface.test.ts`).
  3. Five ADMIN routes that proxy company-shaped aggregate data from the admin namespace (`company-console`, `company-workspace`, `company-live-preview`, `company-evidence-archive`, `company-evidence-record`) sit outside `app/api/company/**` so the company-scoped privacy tests never scanned them — now checked for `pseudonym_id`/`worker_identity_id`/`raw_hash` in any select, and for raw `payload`/`payload_sample` spread directly into a response.
  No code fixes were needed — Task C of the RLS-04 sprint found no correctness bugs; the existing route guards, page-level layouts (B137, MYKORA-01, B168-P3), and RLS policies already implement defense-in-depth correctly. **What this proves:** static/structural correctness of the app-layer guard code as it exists in the repo today. **What this does NOT prove:** runtime behavior of an actual authenticated cross-tenant request through PostgREST/GoTrue (requires live fixtures/secrets — explicitly out of scope per RLS-04's red lines), or worker-vs-worker isolation (`personal.*`, reserved for RLS-05).

**RLS negative testing, worker-vs-worker, local direct-Postgres (RLS-05, `tests/integration/rls-worker-isolation.test.ts`, added 2026-07-04):** Mirrors the RLS-03 direct-Postgres approach for the `personal.*` tables RLS-03 explicitly excluded. Two synthetic WORKER identities (fabricated `auth_user_id` UUIDs, no real Supabase Auth user — `auth_user_id` has no FK to `auth.users`) are created under one shared synthetic tenant, then queried via a transaction-local `request.jwt.claims` GUC (`{ sub, app_metadata: { kora_role: 'WORKER', kora_tenant_id } }`) — same mechanism as RLS-03, extended with the `sub` claim so `auth.uid()` resolves. Scope: `personal.worker_identity` (direct `auth_user_id = auth.uid()` policy) and `personal.worker_pib` (the flagship worker-owned-impact-data guarantee, subquery-based policy — representative of the same pattern used by `worker_profile_private`/`worker_initiative`/`worker_participation`/`worker_cv_share`, not individually re-tested this sprint). Both workers belong to the **same tenant**, so this specifically isolates worker-vs-worker enforcement from the tenant-vs-tenant enforcement RLS-03 already proved. Env vars: `RLS05_PG_URL` / `RLS05_ALLOW_RUN` (own pair, never shared with RLS03's). Skip-safe by default — confirmed locally with neither var set: 1 guard test passed, 8 functional tests skipped, zero DB connection attempted. **Live execution against a running local Supabase instance was NOT performed this sprint** — no local Supabase container was running at implementation time (`supabase status` reported no container), and per this sprint's instructions Docker/Supabase was not started to force it. The skip-safe implementation is complete and ready to run; live execution remains pending an operator with local Supabase already up (see the env var block in `.env.local.example` for the exact command). **What this proves (once run live):** Postgres RLS itself — not application code — rejects one worker's session from reading another worker's `worker_identity`/`worker_pib` rows even within the same tenant. **What this does NOT prove:** any table besides the two in scope (`worker_profile_private`, `worker_initiative`, `worker_participation`, `worker_cv_share`, `uploaded_record_attendee`, `analytics.uef_record`/`impact_unit` remain unverified live — pattern-level, not table-level, proof for the subquery-based ones); GoTrue/Auth sign-in or PostgREST schema exposure (same caveats as RLS-03); company-vs-worker isolation (already proven statically — no COMPANY_ADMIN policy exists on either table at all, see `docs/access-matrix.md`).

## What is NOT proven

- **RLS negative testing exists but only at the direct-Postgres/local level, and RLS-05's live run has not happened yet.** RLS-03 (tenant-vs-tenant, `analytics.*`) is merged and was run live. RLS-05 (worker-vs-worker, `personal.worker_identity`/`worker_pib`) is implemented and skip-safe-verified but has **not yet been executed against a live local Supabase instance** — see the RLS-05 entry above for exactly what's pending. Neither runs through PostgREST or GoTrue. Treat "RLS negative testing" as partially, not fully, closed until RLS-05 has an actual live run recorded here and RLS-06 lands.
- **RLS-04 (app/API-level tenant enforcement) is static/structural only, not a runtime/PostgREST proof.** It confirms every route's *source code* derives tenant/worker identity from session `app_metadata` rather than client input, and that no route offers an alternate auth path into another role's data. It does not exercise an actual HTTP request against a running server with a forged/cross-tenant JWT through PostgREST or GoTrue — that would require live fixtures/secrets, explicitly deferred. Highest-priority routes for a future authenticated E2E extension of `authenticated-smoke.spec.ts`/`golden-admin-company.spec.ts`: `/api/company/workspace`, `/api/company/kora-index/history`, `/api/worker/pib`, `/api/worker/dynamic-cv` — cross-tenant/cross-worker request with COMPANY_B's or a second worker's token should return 403/404/empty, never COMPANY_A's or another worker's data.
- **No authenticated E2E has been run against Production** — only against local dev (backed by real staging Supabase). The mechanism exists (`E2E_BASE_URL` + production guard, wired GOLDEN-03B) but has not been exercised against the actual Production URL.
- **COMPANY_A/COMPANY_B E2E and manual Production checks are incomplete** — see `GOLDEN_PATH.md` for detail. COMPANY_B is not just untested, it doesn't exist yet.
- **No automated test exercises the golden path's data-bearing steps** (upload, UEF approval, scoring run, Decision Pack generation) end-to-end. `tests/unit/b103-golden-path.test.ts` — despite its name — only checks that static files exist; it does not call the real API. Do not cite it as functional golden-path coverage.
- **Lint status was not re-verified in this reconciliation pass.** A prior (now-stale, unmerged) audit catalogued specific ESLint error counts and React anti-pattern locations; those numbers are not restated here as current — re-run `npm run lint` rather than trust an old count.
