**RLS negative testing, worker-vs-worker, local direct-Postgres (RLS-05, `tests/integration/rls-worker-isolation.test.ts`, merged to `main` 2026-07-04):** Mirrors the RLS-03 direct-Postgres approach for the `personal.*` tables RLS-03 explicitly excluded. Two synthetic WORKER identities (fabricated `auth_user_id` UUIDs, no real Supabase Auth user — `auth_user_id` has no FK to `auth.users`) are created under one shared synthetic tenant, then queried via a transaction-local `request.jwt.claims` GUC (`{ sub, app_metadata: { kora_role: 'WORKER', kora_tenant_id } }`) — same mechanism as RLS-03, extended with the `sub` claim so `auth.uid()` resolves. Scope: `personal.worker_identity` (direct `auth_user_id = auth.uid()` policy) and `personal.worker_pib` (the flagship worker-owned-impact-data guarantee, subquery-based policy — representative of the same pattern used by `worker_profile_private`/`worker_initiative`/`worker_participation`/`worker_cv_share`, not individually re-tested this sprint). Both workers belong to the **same tenant**, so this specifically isolates worker-vs-worker enforcement from the tenant-vs-tenant enforcement RLS-03 already proved. Env vars: `RLS05_PG_URL` / `RLS05_ALLOW_RUN` (own pair, never shared with RLS03's). Skip-safe by default (confirmed with neither var set: 1 guard test passed, 8 functional tests skipped, zero DB connection attempted). **Live run (RLS-05B, 2026-07-04):** executed against local Supabase (migrations `001`–`028`, `030`, `031` applied) — **9/9 tests passed** (`RLS05_ALLOW_RUN=true RLS05_PG_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres npm test -- tests/integration/rls-worker-isolation.test.ts`).
